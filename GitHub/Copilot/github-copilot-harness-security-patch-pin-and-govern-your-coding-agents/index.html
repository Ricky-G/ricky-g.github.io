GitHub Copilot Harness Security: Patch, Pin and Govern Your Coding Agents

This post was last updated on 2026-11-22. Some of its content may be outdated.

TL;DR

In one week VS Code fixed ten security advisories, eight of them involving MCP servers, agent tools or the agent host, and froze the Local harness for removal in February 2027. Visual Studio moved Copilot Chat onto the Copilot harness, Copilot CLI tied its built-in MCP server to policy, and Git fixed a clone bug that an agent can trigger just by following Git’s own advice.

Treat the editor fleet like any other agent runtime. Patch to a version floor, pin everyone to the Copilot harness (the one that enforces managed sandbox and permission policy), police MCP, permissions and customisations through Copilot’s managed settings, and prove it with diagnostics, telemetry and a test you expect to fail.

In a hurry? Jump to the version floor, the managed baseline or how to prove it, then come back for the why.

Three weeks ago, in Part 2 of my GitHub Copilot agents guide, I described a Copilot session as three choices: a harness, where it runs and a model. For an organisation relying on Copilot’s managed runtime controls, the choice of harness matters.

The editor used to be the place you typed code. Now it hosts an agent that starts MCP servers, calls tools, runs terminal commands and clones repositories on your behalf. That makes your editor fleet an agent runtime, and an agent runtime needs what any other runtime needs: a patch level, a supported configuration and a policy you can prove. This post is the baseline I’d hand a platform team rolling coding agents out to hundreds of developers.

The guidance below draws on release notes, advisories and docs available on 20 November 2026.

Ten advisories in one patch

VS Code 1.145.3 shipped fixes for ten GitHub security advisories, all published on 10 November. Four of them sit squarely in the agent stack:

The MCP installation links advisory, CVE-2026-114171, covers crafted vscode:mcp/install links. An input definition could run a command once the user approved the install. Its CVE base score is 8.8.

The MCP elicitation notifications advisory, CVE-2026-120779, covers the fallback notification for MCP elicitation. Server-controlled text could become a clickable VS Code command link; exploitation required a user to click it. Its base score is 9.6.

The legacy SSE endpoints advisory, CVE-2026-119983, covers the MCP client’s legacy SSE transport. A server could provide an endpoint that directed later requests somewhere unintended. Its base score is 8.8.

The agent-originated local commands advisory, CVE-2026-120782, covers the Agent Host. Local-command syntax in an agent’s message could run without the expected terminal approval. Its base score is 7.8.

Four more involve agents indirectly. Three let a workspace start an MCP server without a trust prompt: a network workspace file treated as trusted, a __proto__ key in .vscode/mcp.json or settings.json, and a value that switched Workspace Trust off. The fourth let the agent-driven browser upload local files without path approval. The last two fixes cover the serve-web server and JavaScript debugger auto-attach.

A note on scores: the figures above are Microsoft’s base scores from the CVE records. GitHub’s advisory pages show lower temporal scores for the same issues, so your scanner may report 8.3 where the CVE record says 9.6.

Pin: the harness is now the policy boundary

The Copilot harness has been the default for new sessions since VS Code 1.143. It’s built on the Copilot SDK and runs in the Agent Host, the process that runs Copilot sessions. VS Code 1.146 deprecated the Local harness: it’s functionally frozen and will be removed in February 2027, along with the vscode.temporaryDefaultToLocalHarness setting.

The reason matters more than the date. The 1.146 release notes say the Copilot harness “enforces managed sandbox and permission policies that the Local harness doesn’t”. The third-party harnesses are no better from a policy point of view: VS Code 1.147 notes that Claude and Codex sessions “run without Copilot’s managed permission, sandbox, MCP, and plugin controls”. Under Copilot managed settings they’re off unless you permit them with vscode.allowedHarnesses, which for now works only in file-based or MDM-managed settings. It doesn’t override temporaryAllowLocalHarness: false, so the baseline below keeps Claude and Codex off for everyone.

One runtime, several clients

The Copilot SDK isn’t just VS Code’s engine. VS Code’s docs describe it as the shared agent runtime behind VS Code, Copilot CLI and the Copilot app, and Visual Studio 18.12 joined them: “Through the SDK, Copilot in Visual Studio now runs on the Microsoft Copilot harness.” The new Visual Studio chat reads AGENTS.md at the solution root, uses your organisation’s Copilot custom instructions, lets you switch individual MCP tools on and off, and keeps a separate Copilot trusted-paths list that organisations can manage through policy. That new chat is the default for eligible accounts, but it respects an account with editor preview features turned off, and developers can switch back under Tools > Options > GitHub > Copilot > Copilot Chat.

The runtime is shared. The policy channels aren’t.

Same runtime, different levers. Copilot’s managed settings reach Copilot CLI, VS Code, the Copilot app and, for some keys, Copilot in the cloud and JetBrains IDEs. Visual Studio isn’t on that list, so it needs its own Group Policy baseline alongside the GitHub policies that apply everywhere.

One more thing about levers: device policies and managed settings aren’t interchangeable. VS Code’s enterprise guidance warns that a delivered value “does not establish that every harness enforces it in the same way”, and where both set the same control, the enterprise-managed setting wins. I write the rules in Copilot’s managed settings and keep VS Code device policies for editor-only controls such as UpdateMode and ChatApprovedAccountOrganizations, rather than setting the same control in both places.

Patch: set a version floor

Here’s the floor I’d set today:

  • VS Code: 1.145.3 or later fixes ten advisories, eight of them agent-related. Version 1.147.0 is the current stable.
  • Copilot CLI: 1.0.112 or later removes the built-in GitHub MCP server when policy turns MCP off, and sub-agents respect the session credit limit. Version 1.0.114 is current.
  • Visual Studio 2026: 18.12.1, or 18.11.4 if you’re staying on 18.11. The release notes list the Git for Windows fixes under 18.11.4, so check that MSRC lists your 18.12 build for CVE-2026-111760. Version 18.12 moves Copilot Chat onto the Copilot harness.
  • GitHub Copilot for JetBrains: check the applicable MSRC update guidance for CVE-2026-83953, a local information disclosure, and confirm the fixed version for your installation.
  • Git, everywhere: 2.56.1 or the patched release for your series fixes code execution when cloning a malicious repository.

Three things make the floor stick:

  • Keep updates flowing. VS Code “releases weekly updates with new features, bug fixes, and security patches”, so a floor beats a pin. If you’ve set UpdateMode to manual or none to control rollout, you own the patch cadence, including the next Tuesday fix.
  • Set a managed minimum version. VS Code’s AI settings guide describes requiring a minimum VS Code version before AI features are available, which keeps Copilot off until the client is updated. Adding sandbox to Copilot’s managed settings also blocks connections from clients older than Copilot CLI 1.0.93, VS Code 1.141.0 and the Copilot app 1.1.26, but that’s well below this floor, so treat it as a backstop for the oldest clients.
  • Refuse stale policy. forceRemoteSettingsRefresh: true makes clients fetch server-managed settings at startup. In VS Code, Copilot features are blocked until that refresh succeeds. Deliver it by MDM or file so it applies from a device’s first start.

What each block does, and the traps I’d watch for:

  • MCP. The “MCP servers in Copilot” policy decides whether MCP servers run at all, and it’s off by default. When you turn it on, make allowedMcpServers the main control rather than “Registry only”: GitHub’s docs say registry enforcement matches only names or IDs, which users can bypass by editing configuration files. Match by serverUrl or serverCommand, because users choose server names, and list the URLs of any Copilot connectors you use, because the allowlist blocks those too. The sample permits remote servers only; add an exact, reviewed command and arguments for each approved local server. Visual Studio is the exception: managed settings don’t reach it, but registry enforcement does from 18.4, so decide deliberately whether to keep “Registry only” for Visual Studio users. Two gaps to know: GitHub’s documentation says the allowlist doesn’t cover MCP servers defined in repository custom agent profiles; use the cloud agent firewall to restrict their required domains and verify other execution environments separately. The built-in GitHub MCP server is exempt from the allowlist and denylist, although Copilot CLI 1.0.112 removes it when organisation policy turns MCP off.
  • Install links. The 1.145.3 patch fixes the vscode:mcp/install bug. A link opens the server details editor so the user can review the configuration before installing. On supported clients, an allowlist also limits which non-default servers can be installed or run.
  • Permissions. disableBypassPermissionsMode: "disable" neuters --yolo and --allow-all in Copilot CLI and turns off chat.tools.global.autoApprove in VS Code so it can’t be re-enabled. It doesn’t block assisted permissions, so decide separately whether to set permissions.disableAssistedPermissionsMode. Rules follow deny, then ask, then allow, and once any managed rule exists, an unmatched operation asks for approval. In VS Code these granular rules apply to Agent Host sessions, which is one more reason to pin the harness. VS Code 1.147 and Copilot CLI 1.0.111 also accept regular expressions in shell rules.
  • Sandbox. failIfUnavailable with enabled makes the sandbox mandatory: if Copilot can’t enforce it, model and tool execution stop instead of running unsandboxed. allowBypass: false stops users opting out mid-session, and sandboxMcpServers puts local MCP servers inside it too. Turning the sandbox on doesn’t block outbound network access by default, so add sandbox.userPolicy.network restrictions such as allowOutbound: false where a team can live with them. On Windows, host rules and environment variable masking need local network access, so test before you set allowLocalNetwork: false.
  • Masked environment variables. This one is a developer setting, not a managed key. In VS Code 1.146, chat.agent.sandbox.credentials.envVars takes variable names, never values, and tools see placeholders; the real values are restored only in HTTPS requests to the hosts you list in injectHosts. Copilot CLI has the same idea under /sandbox. Masking only works while the sandbox is on, so the admin lever is forcing the sandbox, and the developer lever is a masking list you ship in your standard setup.
  • Customisations. strictPluginOnlyCustomization blocks standalone skills, custom agents, hooks, MCP servers and, since 1.146, canvas extensions from user and project sources, so they arrive only through plugins or managed settings. Plugin-only isn’t a marketplace allowlist, so pair it with strictKnownMarketplaces, which also switches off the built-in marketplaces. Test both against your repositories’ skills, agents, hooks, MCP configuration and instruction files before you enforce them.

Git is part of the agent runtime

Agents clone repositories, run Git commands and read Git’s error messages. On 10 November Git released 2.56.1, with backports down to 2.50.2, fixing six vulnerabilities. The one that matters most here, CVE-2026-111760, allows code execution when cloning a malicious repository. For a recursive clone, the attacker’s code can run during the clone. For a non-recursive clone, Git can report an error and suggest running git status, and following that advice runs the attacker’s code.

That’s exactly the kind of helpful hint a coding agent follows without a second thought.

A delivered setting isn’t an enforced one. VS Code’s policy guide says the diagnostics report “does not prove that a restriction applies to every workflow or agent harness”. Every control gets a test you expect to fail.

  • Delivered. On a test device, run Developer: Policy Diagnostics in VS Code. It shows the applied and non-applied policy tables and the account policy gate, and Developer: Sync Account Policy forces a refresh. VS Code’s guidance pairs it with /sandbox policy in a Copilot session.
  • Enforced. Keep a canary script: open an install link for an unlisted MCP server, ask the agent to read a dummy file covered by a canary deny rule such as Read(~/copilot-canary/), start Copilot CLI with --yolo (1.0.110 and later warn when the flag is ignored), and try to start a Local harness session. Never test with the real rm -rf rule. Each one should fail, every time, and the approved workflow next to it should work.
  • Covered. The Copilot usage metrics API reports last_known_ide_version, last_known_plugin_version and the last known CLI version per user, which is how you find laptops below the floor. Data arrives within two full UTC days. The dashboards don’t include Copilot CLI usage, so use the API.
  • Changed. The audit log records policy changes as copilot.cfb_enterprise_settings_changed and copilot.cfb_org_settings_changed, but those events don’t say which setting changed. Server-managed settings live in copilot/managed-settings.json in your .github-private repository, so require pull request review on that file and the commit history gives you the diff the audit log doesn’t. The log keeps 180 days, so stream it to your SIEM.
  • Observed. The managed telemetry block sends OpenTelemetry to your collector. capture.identity attributes activity to a user and machine; review all telemetry and content-capture settings separately before deploying it. Metrics such as github.copilot.tool.call.count, github.copilot.mcp.server.connection.count and github.copilot.sandbox.operation.count show trends, but GitHub describes sandbox metrics as “not a complete audit log”.
  • Spent.** User-level budgets always hard stop. Cost centre, organisation and enterprise budgets only block if “Stop usage when budget limit is reached” is ticked, and it’s off by default. Copilot CLI’s --max-ai-credits is a soft, user-set session limit, which /compact (1.0.110) and sub-agents (1.0.112) now respect.

Patch first, then policy. Patching is urgent and low risk. Policy is neither: pilot it with a canary group so the first person to hit a deny rule is on your team, not a developer with a release due. Enforce the harness well before February, so the Local harness removal is a non-event.

Nine checks before you call it done

  1. Versions. Every VS Code client is on 1.145.3 or later, Copilot CLI on 1.0.112 or later, and Git on 2.56.1 or the patched release for its series, including images and runners.
  2. Harness. Sessions run on the Copilot harness, and Local, Claude and Codex are off. If a team needs Claude or Codex, treat it as a separate, documented device configuration and test what it allows, because it can’t sit alongside temporaryAllowLocalHarness: false.
  3. MCP. Servers run from an allowlist matched by URL or command, subject to the built-in server and custom agent profile exceptions. Cloud agent firewall rules restrict the required domains for those profiles.
  4. Permissions. Bypass mode is disabled, and risky operations sit in deny or ask rules.
  5. Sandbox. It’s required, it can’t be bypassed, and local MCP servers run inside it.
  6. Secrets. Developers have a standard masking list for the environment variables that hold credentials.
  7. Customisations. Plugin-only customisation and the marketplace allowlist have been tested against your repositories’ skills, agents, hooks, MCP configuration and instruction files before enforcement.
  8. Proof. A canary shows each control blocks what it should, and the usage metrics API helps identify reported clients below the floor. Last-known versions and delayed reports aren’t a complete device inventory.
  9. Visual Studio. It has its own Group Policy baseline, because GitHub doesn’t list Visual Studio as a managed settings client, and you know which developers are on the new Copilot chat.

My take

Most enterprise conversations about coding agents start with the model. I’d start with the harness. The model decides how good the suggestions are; the harness decides whether any of your policy applies. Standardise the harness before you standardise the model.

I’d also stop thinking about version pins. With weekly releases and Patch Tuesday fixes, a pin is a liability within a month. Set a floor, let updates flow above it, and use the managed minimum version and the usage metrics API to catch anything that falls behind. The Copilot harness isn’t immune either: in October, VS Code 1.141.1 fixed a flaw where it could auto-approve edits to hook and agent-definition files, and this month’s agent-originated command bug lived in the Agent Host that runs it. Pinning the harness only works alongside patching.

A few caveats. The policy surface is genuinely confusing: GitHub policies, Copilot managed settings, VS Code device policies and Visual Studio’s Group Policy overlap, and a value that reaches a device isn’t proof that every harness enforces it. Some controls, such as masking environment variables, are still developer settings. The MCP allowlist has a gap for custom agent profiles in cloud sessions. And the baseline will drift, so I’d put a monthly review in the calendar rather than treat this as a one-off.

If I had one week, I’d patch everything on Monday, turn on the managed settings for a canary group on Wednesday, and spend Friday breaking them.

Key Takeaways

  • VS Code 1.145.3 fixed ten advisories, eight of them involving MCP servers, agent tools or the agent host. Make 1.145.3 the floor, with Copilot CLI 1.0.112 and Git 2.56.1 alongside it.
  • The Copilot harness is the policy boundary. The Local harness is frozen until its removal in February 2027, and Claude and Codex sessions run without Copilot’s managed controls.
  • Put the baseline in Copilot’s managed settings: harness, MCP allowlist by URL or command, permissions, mandatory sandbox, plugin-only customisation and telemetry.
  • Visual Studio now defaults to the same runtime but sits outside managed settings, so give it its own Group Policy baseline and check which chat experience your developers actually use.
  • Patch Git wherever agents clone: a non-recursive clone plus a helpful git status hint was enough to run an attacker’s code.
  • Prove it three ways: Policy Diagnostics for delivery, a canary for enforcement, and the usage metrics API, audit log and OpenTelemetry for coverage.
