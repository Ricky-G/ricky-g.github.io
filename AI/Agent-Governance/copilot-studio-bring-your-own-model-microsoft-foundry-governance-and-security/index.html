Copilot Studio Bring Your Own Model: Microsoft Foundry Governance and Security

This post was last updated on 2026-11-26. Some of its content may be outdated.

TL;DR

Copilot Studio can use a model you host in Microsoft Foundry in a prompt through bring your own model (BYOM) on the standard harness. That doesn’t replace the agent’s primary orchestration model, and the Microsoft Copilot harness doesn’t support the prompt tool.

BYOM gives your platform team control over the deployment and its applicable guardrails, quota, diagnostics and Azure costs. Agent orchestration, identity and sharing remain with Copilot Studio and the wider Microsoft governance tools.

The documented connector uses an API key. A dedicated Foundry resource contains the risk of a resource-wide key better than a project in a shared resource.

In a hurry? Jump to the resource decision or the nine go-live checks, then come back for the detail.

A question I keep getting from AI platform teams goes like this: makers are building agents in Copilot Studio, our models live in Foundry behind our guardrails, so if Copilot Studio used our Foundry models, could we govern it like everything else?

It’s a fair question, and the answer is “partly”. Copilot Studio calls a Foundry model mainly from inside a prompt, and that one connection decides a lot about what the platform team controls and where the Foundry should sit. In this post I’ll walk through where Foundry models plug in, what that puts in the platform team’s hands, what it leaves with the Copilot Studio and Microsoft 365 admins, and why I’d give it a dedicated Foundry resource.

The product details below were checked against Microsoft Learn on 20 November 2026, after this year’s Ignite announcements.

Two control planes, one bridge

Copilot Studio runs on Power Platform. Foundry runs on Azure. Each has its own control plane, and neither governs the other. A Copilot Studio agent can reach Foundry in four ways, and two of them put your Foundry model inside Copilot Studio:

  • A prompt with bring your own model. The prompt uses your selected Foundry deployment every time it runs.
  • A generative answers node on Azure OpenAI on your data (preview). A classic data option inside a topic, on the standard harness. It’s the older route, and I’d keep it out of new designs.
  • A connected Foundry agent (preview). The Copilot Studio agent hands a task to a Foundry agent, which does the work on its own model, under Foundry’s controls, and returns a result.
  • A connector or HTTP call. The same pattern: a tool call that returns data.

With generative orchestration, the agent’s primary model, picked from Copilot Studio’s list, decides what to do with the result and can write the answer the user reads. A topic, or a prompt set to send a specific response, can pass the prompt’s output straight to the user, so your Foundry model can have the last word. Microsoft’s model selection guidance separates primary model selection from prompt builder models. The connected-agent preview requires the Foundry agent’s Activity protocol endpoint to be enabled.

Copilot Studio now runs agents on three harnesses: the standard harness, the Microsoft Copilot harness and the Customer Conversation harness, which went GA at Ignite. The BYOM documentation is scoped to the standard harness. The Microsoft Copilot harness has no prompt tool at all: Learn marks prompts there as replaced by skills, and upgrading an agent to that harness creates a copy of the agent rather than converting it in place.

The primary model lists differ by harness too. The standard harness defaults to GPT Chat Latest, while the newest models, such as Claude Fable 5.2, appear on the Microsoft Copilot harness list.

What the bridge accepts

BYOM is narrower than most people expect. Here’s what Microsoft documents today:

  • Where it lives. In the prompt tool, a maker selects + in the model list and connects a Foundry model. The prompt then uses that deployment every time it runs.
  • The connector. The connection runs on a Power Platform connector. Its fields match the Azure AI Foundry Inference connector reference, and Learn says to govern it in data policies under the name “Azure AI Foundry”.
  • The API. Chat completions only. The endpoint must end in /chat/completions, and a Responses API URL fails.
  • The models. The GPT-5 family and later models aren’t currently supported. Claude models in Foundry use the Messages API, so a Claude deployment doesn’t fit the connector either.
  • Authentication. An API key, alongside the endpoint, deployment name and base model name. The connector documents no Entra ID or managed identity option.
  • Safety. The prompt’s content moderation setting isn’t available for Foundry models, and Microsoft recommends applying Responsible AI policies in Foundry. Confirm which controls actually apply to the model and API; coverage and behaviour vary.
  • Cost. Foundry charges for BYOM processing separately. Microsoft’s AI Builder billing guidance treats invoking a BYOM prompt as an agent action, without an extra text and generative AI tool processing charge. Other agent activities and licensing or test-panel exceptions can affect Copilot Credit charges.

  • Detect and respond. The security admin and SOC, in Microsoft Defender: agent security posture and threat investigation.

Where should that Foundry live?

Platform teams usually put two options on the table:

  • Option 1: a dedicated Foundry resource for Copilot Studio, in its own subscription.
  • Option 2: a project inside the shared AI platform’s Foundry resource.

Option 2 looks like the natural fit. Foundry projects give teams isolated workspaces that share model deployments under central governance, and Microsoft describes exactly that pattern. But BYOM changes the maths in three ways:

  1. The key is resource-wide. Learn puts it plainly: “Keys are all-or-nothing per resource.” A key that works for the Copilot Studio deployment works for every deployment in the resource, across every project, with no role restrictions.
  2. Key authentication has to stay on. BYOM only offers an API key, so the resource can’t set disableLocalAuth to true, and Learn describes API keys as “Generally not accepted by enterprise production workloads and not recommended by Microsoft.” On a shared platform resource, the whole platform goes back to accepting keys, the opposite of the keyless pattern I wrote about earlier this month.
  3. The endpoint has to stay reachable. The connector isn’t on Power Platform’s published virtual network support list. For this documented connector, plan for a reachable public endpoint and test network restrictions. That absence doesn’t prove that every possible private integration is impossible.

There’s more. The built-in Foundry User role includes permission to list keys when assigned at a scope covering the resource, as do some broader roles. Check effective assignments and inheritance rather than assuming every project user can list them. Guardrails can be attached per deployment, diagnostic settings are set per resource, and model router’s instant access (preview) is configured for the whole resource. Microsoft’s rollout guidance also recommends treating isolation as the production default.

The resource decision

Option 1, a dedicated resource: the BYOM key can reach that resource’s deployments, so keep only the intended workloads there. Key authentication and the required network exception are contained to that resource. Limit who can list keys, attach and test the applicable guardrails, and use resource-level costs for simpler attribution. A separate subscription gives it a separate quota pool, subject to availability and approval.

Option 2, a project in a shared resource: the key can reach other deployments in the resource, while key authentication and the reachable endpoint affect the shared resource. Review effective key-listing permissions, including resource-scoped Foundry User and Contributor assignments. Guardrails are configured per deployment, and quota is shared by subscription, region, model and deployment type. Cost attribution depends on available dimensions; the shared key doesn’t identify the caller.

For most organisations I’d pick Option 1. Option 2 needs a deliberate security review of key scope and network exposure, even if the shared resource already accepts keys.

Who runs the dedicated Foundry

Dedicated doesn’t mean ungoverned. I’d place the resource in the AI landing zone, deploy it from the platform team’s template and apply the relevant management group policies, including the built-in policy for approved model deployments. The documented connection requires key authentication, so a policy that disables local authentication needs a reviewed exception. If the tested network path requires public access, review that exception too. Give each exception an owner and expiry, and track renewal alongside key rotation.

The AI platform team owns the template and its guardrails, using infrastructure as code, approved-model policies and central diagnostics.

The Copilot Studio platform team owns the subscription, deployments and connection. It requests models through the platform’s approval path and manages key rotation and connector data policy.

The security team reviews exceptions and monitors key listing and unusual token use.

Approving and retiring models on two calendars

Copilot Studio and Foundry retire models on different calendars, and BYOM puts you on both.

On the Copilot Studio side, Microsoft runs the calendar. Its standard harness documentation lists 12 November retirement dates for GPT-4.1, GPT-4.1 Mini, GPT-5 Chat, GPT-5 Auto and GPT-5 Reasoning as primary models, with extensions of up to 30 days and GPT Chat Latest as the replacement. FedRAMP tenants, and environments outside the US that restrict cross-region data movement, have an exception for GPT-4.1 and GPT-5, so check your environment’s setting. On the Microsoft Copilot harness, the EU and EFTA exception for GPT-5 Chat ends on 30 November. Affected managed prompt models move automatically by 2 December to GPT-6 Luna, ChatGPT-latest or GPT-6 Reasoning, depending on their tier.

On the Foundry side, you run the calendar. A BYOM prompt points at a named deployment and base model, so swapping the model should be a change you make and test. Plan it before the retirement date: Foundry can upgrade some deployments automatically at retirement, and gpt-4o version 2024-05-13 on Global Standard and Data Zone Standard moves to gpt-5.1, which BYOM doesn’t support. Foundry retired the o-series on 19 November and has GPT-4o and GPT-4.1 on its retirement schedule for January to April 2027.

This month’s headline model shows why the line matters. Claude Fable 5.2 started rolling out in Copilot Studio on 11 November, through Microsoft’s own model list. It appears on the Microsoft Copilot harness list behind the “Anthropic models with data retention” provider setting, which is off by default. A Microsoft 365 admin turns that on, and a Power Platform admin still has to allow the provider’s models for each environment or environment group. Deploying Fable 5.2 in your own Foundry doesn’t change that. BYOM can’t call a Claude deployment directly, because Claude in Foundry uses the Messages API, and Foundry doesn’t apply built-in content filtering to Claude models anyway. “Govern it through our Foundry” simply doesn’t apply to the model everyone’s asking about this month. The decision sits with the Microsoft 365 admin, the Power Platform admin and your model approval board.

  • Agent 365 usage and activity insights are generally available, without an Agent 365 licence, for agents built on Microsoft platforms.
  • Dynamic Agent Risk (preview) sits alongside the agent registry, visible across the Microsoft 365 admin center, Defender, Entra, Intune and Purview.

Nine go-live checks

  1. The agent stays on the standard harness. Any move to the Microsoft Copilot harness has a plan for the prompt first, because that harness has no prompt tool.
  2. The model fits. It serves chat completions, it isn’t GPT-5 or later, and its Foundry retirement date sits beyond your next review, with the replacement planned before Foundry can upgrade the deployment for you.
  3. The resource is dedicated. Its key opens only Copilot Studio’s deployments, and its policy exemptions have an owner and an end date.
  4. Roles are tight and keys rotate. Only the people who manage the connection can list keys. Regenerate the key the connection isn’t using, move the connection to it, then regenerate the other one.
  5. Instant access is reviewed. Model router’s Auto option (preview) is set per resource. Microsoft’s router reference says an empty properties.instant.modelAllowList turns off instant access, including Auto. Check the effect on other instant-access models and test this preview setting; deployed models and other access paths still need governance.
  6. Guardrails are assigned and tested. The prompt’s own moderation setting doesn’t apply to Foundry models. Check the controls supported by the selected model and API rather than assuming uniform coverage. For supported text calls, a request can override the deployment guardrail using x-policy-id; Microsoft’s guardrail guidance notes that this override isn’t available for image input. Review the policies available in the resource.
  7. The connector is allowed only where it should be. The data policy allows “Azure AI Foundry” in the environments that host approved BYOM prompts and blocks it elsewhere, and the connection holding the key is shared only with the makers who own those prompts.
  8. The network path is a decision. Test whether the documented connector can reach the endpoint with your network rules and Power Platform’s current outbound IP ranges. An API Management URL or private path is a lab test, not a design assumption, because the connector is documented for Foundry endpoints.
  9. Both meters and both logs are wired. Azure budgets and diagnostic logs on the Foundry resource, and Copilot Credit tracking and Purview audit on the Copilot Studio side.

My take

I like BYOM for what it is: a way to put a specific model, such as an open-weight or industry model, behind a single prompt, with applicable platform controls on that call. What it isn’t is a way to govern the whole Copilot Studio agent. Its orchestration, identity and sharing still need the controls in Microsoft’s governance map.

Where I push back is the reflex to drop Copilot Studio into a project on the shared platform because it looks tidy on a diagram. The documented BYOM connector needs a key, and a key turns a project boundary into a resource-wide pass. I’d rather run a dedicated Foundry resource with a reviewed key and network exception than reopen the whole platform. It’s the keyless argument from earlier this month applied the other way round: when you can’t remove an exception, contain it.

Two caveats. First, the bridge is narrow and it’s narrowing: no GPT-5 or later, no Claude, no Entra ID, and the GPT-4.1 and GPT-4o models that fit retire in 2027, while new models such as Fable 5.2 arrive on a harness with no prompt tool. Second, the connector is documented for Foundry endpoints only, so an AI gateway in this path is something to prove in a lab before you promise it to anyone.

If I were setting this up today, I’d keep BYOM for the few prompts that genuinely need a model of our own, govern everything else where Copilot Studio governs it, and look again after the next round of harness and model updates.

Key takeaways

  • Copilot Studio can call Foundry models from a BYOM prompt on the standard harness. Its primary orchestration model is selected separately.
  • BYOM gives the platform team control of the call: model version, region, guardrails, quota, logs and token cost.
  • Agent governance and evidence span Power Platform, Microsoft 365, Entra, Purview and Defender. Prompt data sent to Foundry also reaches the deployment.
  • The connection is chat completions with an API key: no GPT-5 or later, no Claude and no Entra ID.
  • Foundry keys are resource-wide, so a project in a shared resource exposes every deployment. Use a dedicated resource with time-bound policy exemptions.
  • Plan for two calendars and two meters: check Copilot Studio model migrations, manage Foundry deployments, and account for Azure processing and eligible Copilot Credit activity separately.
